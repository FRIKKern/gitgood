# Elixir admission and held database identity

The protocol-2 application boundary uses a fixed Root-installed observer before
opening its installation lease. `InstallationGenerationAdmission` accepts only
the supported installation storage path and fixed runtime or maintenance role.
It invokes the isolated system Python executable and fixed installed entry with
one bounded, closed request. The caller supplies its actual BEAM owner PID;
neither executable paths nor observation authority come from the request.
The entry validates all bounded installed module files as Root-owned, regular,
single-link and nonwritable by other accounts before importing. It refuses cache
directories and missing core modules. Isolated Python disables site-package
loading and bytecode writes.

The observer reads the installation's canonical Root-owned admission seal. Its
independently allocated binding, history, lock, service unit, runtime paths,
resource limits and database identity remain separate from ordinary history.
The read-only generation reader validates the completed publication and actual
worker/helper ancestry. The Elixir caller bounds response size and time and
checks its installation, owner, role, pointer, seal and explicit authority flags.
No error response includes the request, configuration, connection parameters or
traceback. Initial admission grants no database lease or lifecycle authority.

`InstallationDatabaseSession` observes an already held Postgrex connection. It
matches the independently expected PostgreSQL cluster, database and limited
owner role, all role flags and memberships, server version, encoding and endpoint.
It records the actual backend PID and birth and requires the granted advisory
lock namespace 1197034575, key 1, two-integer exclusive form. Rechecking uses the
same connection and exact snapshot. Lost ownership, a new backend, changed
database identity or unavailable observation refuses; this module never opens,
reconnects or reacquires a session.

Seven session boundaries and four caller-response boundaries pass. An actual
ordinary Elixir/Postgrex experiment passes seven checks, including contention,
explicit unlock, exact backend termination, replacement backend birth and refusal
to reuse the old snapshot. Four independent custody checks bind the source,
169 pinned dependency files, retained data and empty bounded worker scope. Eight
request boundaries and six module-custody boundaries pass. The custody guard
also passes six actual Linux filesystem checks using an ordinary actor and
independently prepared Root-owned fixtures. The full Linux operator suite passes 312 tests with
twelve platform skips. These results establish the component boundaries.

The actual service VM passes 24 checks across exact manager interruption,
same-boot successor publication and two distinct kernel boots. Actual ordinary
BEAM owners in both worker roles invoke the fixed installed observer. The native
owner holds the independently expected PostgreSQL lease at its exact backend
birth; maintenance contention refuses on both boots. Four independent custody
checks bind 48 current operator sources and verify all fifteen booted fixture
scopes are empty. Separate powered-off disk inspection checks the Root ownership,
mode, link count and exact bytes of 66 installed files without modifying the
original overlay. Failed and superseded experiments remain retained.
The existing `InstallationLease`, application configuration and protocol-1
markers remain unchanged. Application wiring, generation-aware markers and
periodic checks still require implementation and actual interruption evidence.
This component establishes no packaged readiness, lifecycle dispatch, allocator,
deployed authentication, Cloud contract or complete journey acceptance.
