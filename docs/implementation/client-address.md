# Login origin and proxy boundary

The direct-edge production profile has one TLS edge, one loopback web process and one loopback forge. Previously the forge limited every proxied login under the web process's shared socket address. It now authenticates the edge's actual socket client address through the web before selecting a bucket. The 20 attempts per address per fixed minute and 10,000-address bound remain unchanged; they are abuse limits, not measured capacity acceptance.

## Ownership and configuration

Provision one canonical base64 encoding of 32 random bytes as GITGOOD_PROXY_KEY in the edge, web and forge service environments. It is separate from the session and source-credential keys. Neither the repository, browser nor ordinary evidence stores it. Production forge and web startup refuse a missing or malformed key. Rotate the three services together after draining; mixed keys refuse login. Existing issued sessions remain governed by their native credentials.

At the direct edge, overwrite X-Gitgood-Edge-Client with the TLS connection's remote host and X-Gitgood-Edge-Key with the configured secret. Strip caller X-Gitgood-Client-Address/Time/Signature before forwarding. Only the web receives the edge secret; the direct Git route strips all these fields. The sample Caddy configuration describes this exact profile. Its configuration and service environment are private; expanded configuration and debug header logs must not become ordinary evidence.

The web validates the actual srvx Node socket is loopback, verifies the secret with a constant-time comparison, validates one literal IP address, and consumes the edge headers. It removes any caller-supplied native assertions and creates a fresh HMAC over a domain label, address, Unix seconds, method and exact path/query. The API proxy forwards only those assertions. It preserves the original body stream and abort signal. The browser cannot select an upstream; incoming Forwarded/X-Forwarded-For fields do not control the bucket. Broad trustProxy flags are unnecessary.

The forge requires its loopback web peer, exactly one of each assertion, a 30-second timestamp window and the correct SHA-256 HMAC binding before login. It normalizes equivalent IPv4-mapped IPv6 addresses to the same rate bucket. An invalid context returns client_address_unverified before authentication and issuance. Direct unsigned forge or unsigned web login refuses in production. Development without a configured key uses the native socket IP and ignores caller forwarding headers.

## Verification and limits

The backend exercises forged/stale/duplicate/wrong-key/method/path/query assertions, non-loopback peers, equivalent address representations and independent limited buckets. Node checks assert that the edge secret and caller assertions are removed. The copied-production experiment requires Caddy 2.11.7 and validates/runs the committed example. Access evidence omits all request/response headers, and runtime logs are checked against the actual edge secret. The browser workflow in CI runs through this copied installation with its owned HTTPS source fixture; no separate unconfigured development source wire is assumed. It must exercise actual TLS client sockets from two addresses, the 20/21 boundary despite changing spoofed forwarding headers, a valid independent second-client login, direct bypass refusal and normal browser workflows. Unit checks alone do not prove the deployed boundary.

This profile deliberately names a direct TLS edge. A CDN, ingress chain, additional proxy or another runtime needs a separately verified derivation of the actual client address and a corresponding configuration change. The sample does not claim that any Cloud provider's network path has been verified. The key authenticates the assertion, not the user's identity; native authentication still identifies the actual account. The same-host OS/service isolation remains part of the deployment contract.
