# Coordinated offline recovery

Status: implementation in progress; no supported backup or J16 acceptance is claimed yet.

The first recovery profile targets one Ubuntu 24.04 x86-64 installation with PostgreSQL 18.4, persistent native Git storage and one supervised forge runtime. The tested database uses UTF8, the libc locale provider and C.UTF-8. The Windows copied-production experiment remains separate from this Linux operational profile. The backup must preserve the same candidate/schema, database text semantics and public origin on a replacement host; broader compatibility requires additional experiments.

## Exclusion and recovery point

The production runtime owns a dedicated PostgreSQL session and an exclusive installation advisory lease before starting mutation workers, listeners or SSH. Another runtime or offline maintenance cannot obtain that lease concurrently. This enforces the existing single-runtime deployment contract; it is not a distributed leader election service.

Production migrations also obtain the same maintenance lease; they refuse an incomplete restore. The lease guard verifies its original PostgreSQL backend identity and granted lock. Loss stops the guard. The application's supervisor stops and restarts every later worker/listener in order; a persistent process marker additionally refuses another claim while an earlier BEAM or maintenance owner remains alive, even after its database lease disappeared. Markers contain protocol, local host, numeric owner PIDs and kernel process creation identities, and never read or expose process command arguments. Linux identities come from proc start ticks; Windows identities come from GetProcessTimes. A live process with the same PID but a different creation identity is another lifetime, so PID reuse does not falsely preserve the earlier owner. Legacy PID-only records retain conservative live-PID refusal. Foreign, malformed, missing-protocol and inaccessible records fail closed. Unavailable identities and malformed identity maps fail closed. Legacy PID reuse may conservatively refuse maintenance and must not be bypassed without actual ownership evidence. The copied Windows verifier waits for the previous process instance to finish after terminating its owned process tree.

A Linux operational backup requires the supervisor to stop a dedicated cgroup v2 containing the entire native runtime, including Git/Python children that create separate process sessions and pending source workers. The runtime marker records its actual kernel cgroup. Both initial claim and final publication require its cgroup.events to report populated 0 and cgroup.procs to be empty. A missing, root, inaccessible, aliased or still-populated group refuses backup. Keep that group present through the operation. The packaged launcher joins a pre-provisioned empty group before exec; a service supervisor can provide the same contract. A plain process-group signal is insufficient because Git adapters create separate sessions. The offline command then obtains the installation lease and checks the stopped runtime marker before reading stores. A database lease alone does not fence orphaned filesystem writers. External edits to the managed database/repository volumes are outside the supported operation contract. A supervisor kill-mode proof and an interrupted Git/source operation are part of acceptance, not inferred from a stopped HTTP endpoint.

The recovery point is the durable PostgreSQL plus Git state after that write pause. Pending operation records, recovery refs, import intake and encrypted source requests remain included so the replacement runtime can reconcile them. Preserve uncertain source outcomes; a backup cannot invent a missing upstream write receipt.

A killed prepared Git ref transaction can leave a lock that passes fsck but blocks the next write. After validating managed ready repositories, backup rechecks the installation lease and empty native cgroup before moving known HEAD/config/packed-refs/shallow and refs-tree lock files into `.gitgood-interrupted-locks-v1` inside the managed store. Atomic no-replace moves preserve the original inode and bytes with a digest receipt; the quarantine is included in the encrypted backup and restored as private forensic custody. Recovery never publishes a lock's proposed ref content. Native operation records and actual refs remain the reconciliation authority. Live writers, linked/special locks and refusal bounds (1,000 locks, 32 MiB per file, 64 MiB total) prevent cleanup. A stale lock in a ready repository refuses ordinary inventory and restore validation until this offline procedure runs. Unfinished repository/import stores remain preserved; this procedure does not speculate about their contents.

## Required bundle inventory

An independently keyed authenticated encrypted bundle must include a PostgreSQL custom-format dump; every managed repository object/ref/configuration and import/recovery file; SSH host identity; and the configuration/secret material needed for sessions, login-origin assertions, source credentials and their encrypted request journal. Include explicit source CA material where configured. Source-owned Barkpark documents and tasks remain upstream authority and are not copied as native backup-owned records.

Keep replaceable forge/web artifacts and their exact build identity separately from mutable recovery data. Preserve an immutable inventory with file lengths/digests, runtime/schema/format compatibility, source candidate and the actual recovery-point time. Do not place decrypted keys, expanded configuration, TLS private keys, source credentials or the backup decryption key in ordinary evidence.

Restore must authenticate the entire encrypted input and validate bounds, paths, digests, complete inventory and compatibility before importing a database or installing files. Reject traversal, symlinks, duplicate entries, unsupported formats, missing stores and existing unrelated destinations. The backup decryption key remains outside the bundle. Regenerate native Git hook paths for the replacement installation rather than reusing absolute paths from the previous host. Do not declare success from a successful database import alone.

## Operator entry points under verification

The fixed copied-release commands are `bin/gitgood eval 'Gitgood.Release.backup()'` and `bin/gitgood eval 'Gitgood.Release.restore()'`. They load configuration and Postgrex without starting forge workers, SSH or HTTP. The operational implementation currently requires the pinned Node 22.23.3, Linux x86-64, local PostgreSQL 18.4 and matching pg_dump/pg_restore. Environment credentials are passed privately to native database tools; they never appear in command arguments.

Provision the private configuration once with `node scripts/provision-recovery.mjs` in the installation environment. Set `GITGOOD_RECOVERY_CONFIGURATION`, `GITGOOD_WEB_PORT`, `GITGOOD_API_URL`, `GITGOOD_TLS_CERTIFICATE` and `GITGOOD_TLS_KEY`; supply the existing native forge environment and optional explicit source CA. Provisioning selects an explicit setting whitelist, excludes bootstrap passwords/unrelated environment variables, preserves stable installation identity and refuses an existing destination. Protect the directory and files with owner-only modes. Retain the matching code artifacts separately.

For backup set `GITGOOD_RECOVERY_KEY_FILE` to an existing private regular file containing exactly 32 independent random bytes, and `GITGOOD_RECOVERY_BUNDLE` to an absent destination outside all stores. Keep the key outside the encrypted bundle. Stop the full owned runtime cgroup before invoking the command. Backup checks configured custody against the current native environment, decrypts every saved credential/pending sealed request, binds ready database repository UUIDs to real native SHA-1 stores, runs Git fsck, and fingerprints database rows/sequences/schema before and after the dump and again before publication.

For restore create an owned empty database and private installation parent. Set its `DATABASE_URL`, `GITGOOD_RECOVERY_INSTALLATION`, `GITGOOD_STORAGE` to that parent's git directory, the key file and bundle. Supply the normal required release configuration so offline eval can load, without starting services. Complete authentication, compatibility and declared-file checks precede importing that database. An incomplete gate binds the exact ciphertext digest, candidate, installation and target database; runtime, migration and backup refuse any gate entry, including a dangling symlink or inaccessible path. A retry accepts only that same binding, recognizes an already committed database by its full fingerprint, and installs files by atomic no-replace moves or exact-byte comparison. Unexpected files, different bytes or a nonempty unmatched database refuse. Original Git hook paths are rewritten to the new installation using the packaged trusted hook before publication. The native credential/request decryptor verifies recovered key custody before the gate is removed and its directory synced. Source public origin remains unchanged; database and persistent store paths become explicit new-target values.

Start the matching artifacts with the recovered private configuration only after the final command reports complete. That receipt establishes operator completion; J16 still requires the functional replacement-host exercise below. Private configuration, plaintext staging, decryption key and encrypted backup remain recovery materials, excluded from ordinary verification archives.

## Acceptance still required

Recovery also binds the source database encoding, locale provider, collation, character type, provider locale, recorded/actual collation versions and local GNU libc version. A real PostgreSQL experiment produced identical rows and schema fingerprints with C.UTF-8 and C databases while lowercasing the same character differently. Restore now requires matching properties before creating its incomplete gate, importing the database or installing stores. A missing profile and a stale recorded collation version refuse. Exact original-candidate recovery remains required; prior experimental bundles are not upgraded implicitly. This check is compatible-profile refusal, not a locale conversion facility.

The file-bundle primitive uses a versioned AES-256-GCM envelope with a fresh 12-byte nonce and a separate 32-byte key. Its canonical encrypted inventory limits entries to 100,000, manifest bytes to 16 MiB and total file bytes to 16 GiB; these are format refusal bounds, not measured workload capacity. Full tag authentication and all declared file digests precede extraction. Private staging is published without replacing an existing destination; failed final quiescence leaves no published backup. This primitive alone does not dump a database or establish a complete recovery point.

The database experiment fingerprints ordered native table rows, sequence values and schema DDL. PostgreSQL 18.4 reparses a literal varchar-array cast into per-element text casts and flattens the native asset size-bound AND grouping when restoring its own dump. The initial exact schema-text check refused this difference; original schemas and the rejected comparison are retained. Only these specific equivalent representations and random pg_dump restriction keys are normalized. Literals, bounds, names, operators, constraints and all remaining DDL still affect the hash; adversarial changed-bound/value/operator tests must refuse equality. See [PostgreSQL array/type expressions](https://www.postgresql.org/docs/18/sql-expressions.html#SQL-SYNTAX-ARRAY-CONSTRUCTORS). No general-purpose SQL equivalence claim is made.

Prove complete-process exclusion; interruption/cleanup; encrypted exact-byte archive and wrong-key/corruption/incomplete/incompatible rejection; replacement-host installation with separate artifacts and stores; preserved refs, collaboration, release assets and SSH identity; source credential/journal decryption; denied users; authorized clone and a new push. Set bounded pilot data-loss and recovery-time targets before measurement, then record actual results. Cloud routing and managed lifecycle remain J14/J15 work.

References: [PostgreSQL advisory lock semantics](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS), [PostgreSQL dump scope](https://www.postgresql.org/docs/18/app-pgdump.html), and the pinned Postgrex/DBConnection implementations inspected for connection behavior. The database lock excludes cooperating clients; it does not replace OS process-group ownership.
