# Periodic generation guard

Implementation work, with no application or journey acceptance established.

Keep one ordinary generation observer alive beneath the actual BEAM owner. Its
initial capture performs complete independent persistent identity admission.
Retain the completed publication, full bounded history snapshot, actual owner
birth and service scope in that observer. Subsequent checks reobserve ancestry,
service scope, publication/history and persistent file metadata. They open no
database connection and take no lifecycle lock. The application's already held
Postgrex session independently checks database identity, backend birth and lease.

Hash executable contents and query independent database identity during capture.
During subsequent checks, compare exact file identities, size, times, ownership,
mode and link count against that validated capture. Storage and staging directory
contents may change during legitimate application work; their directory identity,
ownership and mode remain bound. Configuration and SSH key inventory remains
closed. A changed or unavailable observation permanently poisons the guard; it
cannot recapture or silently adopt another generation.

The fixed installed entry and bounded stream emit one initial admission followed
by matching generation tokens. Their request cannot select a command, program,
environment or seal. A linked Elixir monitor bounds initialization, message size
and heartbeat age, validates the actual owner and rejects changed tokens. Python
site loading and bytecode writes remain disabled. Application supervision wiring
requires implementation. Refusal must stop the application and retain its marker.
Generation-aware markers, lifecycle admission, recovery and packaged functional
checks remain required under decision 0018. A periodic guard grants no lifecycle,
writer or readiness authority, and performs no writes, cleanup or signals.
