# Actual native runtime workers

`Gitgood.NativeRuntime` is a fixed permanent application that connects actual
product workers and HTTP/SSH listeners to original lifecycle ownership. It does
not accept a worker list, program, callback, input path or authority override.
Running product, maintenance or runtime applications refuse rather than being
reused. The [default application startup](native-default-startup.md) now shares
this fixed runtime factory; its actual normal-release startup and failure require
current installed evidence, separate from complete lifecycle acceptance.
`Gitgood.Release.native_runtime/0` prints only the safe activation outcome and
keeps that original BEAM running; ownership loss must terminate it.

## Startup before mutation workers

The initial native root contains lifecycle-aware runtime ownership startup,
a Repo pinned to `pg_catalog, public`, and a pending runtime coordinator. It
starts no product mutation/reconciliation worker or listener during that init.
The caller then makes one fixed `activate` request, with a hard 60-second process
deadline. Repeating activation while running or after completion stops the
permanent application and whole BEAM.

The coordinator captures the original startup PID after the supervisor has
completed init. It checks current ownership, clean compiled candidate, the
Root-controlled flat package inventory and actual exact public schema. The
[migration inventory](../CODEBASE.md) is shared with maintenance; it rejects
unknown/nested entries, symlinks, hard links, writable files and malformed or
unbounded declarations. This check grants no compatibility or migration authority.

Only then does the coordinator add fixed telemetry and product children, checking
the same original startup PID before and after each start. The common
`RuntimeWorkers` list also serves the existing development application, preserving
its worker order and legacy lease behavior. Native children remain permanent in
the existing root with zero permitted restarts. No replacement ownership helper,
lease or failed child is adopted. Any refusal/failure ends the original BEAM.

Native readiness checks the original startup's monitor/lease/fence and exact
compiled schema in the fixed SQL namespace. It cannot use the legacy installation
lease as a substitute. Activation observes internal readiness but reports public
activation and complete journey acceptance false.

## Installed evidence

The hosted `native-runtime-effects` case runs actual migration and first-owner
creation first, then activates the real runtime worker/listener tree under the
same live controller, boot and generation. Before activation, Root requires
listeners absent and captures the original lease/Repo SQL and kernel identities.
The fixture then checks actual internal readiness and anonymous denial, performs
signed owner login, creates a private repository, and uses real Git clients for
HTTP push/readback and SSH readback. Session revocation must remove access.
Tokens, passwords, private keys and response bodies never enter ordinary receipts.
HTTP redirects and ambient proxies are refused; SSH uses the independently
captured host key with strict checking.

After original helper loss, the whole BEAM, captured backend identities and HTTP/
SSH listeners must be absent. Original ownership records and marker inodes remain
retained; the fixture manager alone performs its bounded descendant cleanup.
This is internal HTTP and direct SSH evidence, not public TLS, frontend, complete
installation, activation or recovery acceptance.

`native-runtime-schema-refusal` removes one expected migration version in the
owned synthetic database before the runtime owner launches. The actual runtime
coordinator must refuse before product workers/listeners, end the original BEAM,
leave captured backends absent and preserve the running `verify` lifecycle head
and snapshot. No repository may be created and the failed stage cannot advance.

Focused checks exercise malformed package/build declarations, replay/status
refusal, the actual OTP runtime loader and actual coordinator control flow. Root,
inventory and database dependencies in the latter local checks are explicit
stand-ins. Only current passing installed artifacts establish the real service,
SQL, network and Git outcomes. Existing inspection/staging/verification journal
receipts remain synthetic metadata. Complete lifecycle dispatch and interrupted
effect reconciliation, public activation/enrollment, reboot and replacement-host
recovery and full J14/J15 acceptance remain required.
