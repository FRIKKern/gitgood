# D06 Application packaging

Status: experimental local contract; managed Cloud contract remains open. Owner: autonomous Gitgood implementation. Decision date: 8 October 2026.

## Decision

Package one clean candidate as an Elixir/OTP release plus TanStack SSR output, static client assets and locked production Node dependencies. Run Git and Python as bounded subprocess dependencies. Use persistent PostgreSQL and bare Git stores outside replaceable artifacts. Bind services to loopback behind one HTTPS origin and route Git transport directly to the forge. Require matching build identity and readiness before traffic.

A combined source-running development process cannot establish production behavior. A Windows release does not establish Linux compatibility, so CI builds and exercises its own Linux artifacts. Containers are an alternative product packaging layer after the same artifact contract passes. The [isolated CI container boundary](../implementation/isolated-ci.md) does not itself supply a containerized Gitgood application package.

## Experiment and evidence

The reproducible experiment is [production.md](../deployment/production.md) and scripts/verify-production.mjs. It installs copied artifacts in a fresh directory without application source, migrates a fresh database, runs real browser/Git collaboration, restarts services and probes persistence/readiness failures. Its sanitized receipt identifies candidate, dependency/spec hashes, actors, runtime and outcomes. The run finish record links the passing candidate evidence; this decision itself is not a live verification ledger.

## Barkpark Cloud audit

Read-only source inspected at Barkpark commit 68412eff4a0eb5a22cdc8e755e437c8dc66ceed3:

- cloud/lib/barkpark_cloud/registry/site.ex ships framework values nextjs, astro and static, with always_on scale mode. Node/container vocabulary alone is not proof of a shipped arbitrary workload.
- deploy/site-deploy-node.sh expects Next.js standalone server.js and .next/standalone. TanStack's fetch entry and static assets require a distinct supported adapter.
- cloud/lib/barkpark_cloud/sites/deploy.ex supports existing static/node deployment targets and artifact hashing. Its scoped environment contract does not establish Gitgood's two services, database/storage ownership or secret configuration.
- Existing Node blue/green replacement must not overlap forge versions against the same stores without protocol compatibility evidence.

No Barkpark code or deployment was modified. Gitgood cannot be truthfully registered as Next.js. Cloud support needs an explicit workload contract: paired artifact identity/digests, CPU/runtime targets, required binaries, private secret/environment configuration, persistent database/Git volumes, TLS routing and blocked internal endpoints, quiesced upgrades/reconciliation, readiness, ownership, rollback and restore. No unverified Cloud endpoint is adopted.

## Support-instance audit — 11 October 2026

A further read-only audit of the same Barkpark source commit examined `cloud/lib/barkpark_cloud/web/router.ex`, `internal/provisioner/support.go`, `internal/provisioner/worker.go`, and `internal/cli/cloud/support.go`. The supported `POST /v1/fleet/supports` provision action requires a same-team parent Barkpark and its existing administration credential. Its job creates a Barkpark instance from the configured warm image, copies the parent dataset, and installs a parent-connected fleet agent.

The route does not accept a separately bound provider project, generic native workload, clean Ubuntu image, GitHub Actions registration, or independent CI secret/storage contract. The observed Hetzner action catalog also exposes existing-server operations rather than a general server-create action. These capabilities do not establish an isolated Gitgood CI or pilot allocation. No provisioning, production mutation, or SSH operation was performed by this audit.

The next infrastructure contract needs explicit ownership of the provider project, host and credentials, a supported image/runtime, fixed lifecycle actions, and retained recovery responsibility. A dedicated CI allocation must stay separate from the pilot's application credentials and data. Current access, inventory and blockers belong in the delivery ledger, not in this historical audit.

## Remaining uncertainty

The experiment covers local copied artifacts and Linux CI. It does not prove host hardening, actual managed TLS/proxy deployment, signatures, replacement-host restore, power-loss durability or multi-instance operation. Those remain M6/M7 gates. A pinned Cloud adapter should be built only after its supported contract and isolated deployment fixture exist.
