# Fixed native upgrade commands

Status: implemented with scoped installed CLI verification; current required CI pending.

The current upgrade library has scoped actual transition, unhealthy candidate,
previous-code recovery, partial migration and lost-acknowledgement evidence. Its
callers still use fixture drivers. Codex primary agent chooses fixed operator
commands for initial execution, previous-code recovery and forward repair of an
already enrolled working installation. This is a J15 implementation dependency;
it adds no release scope and does not establish first-install enrollment or Cloud.

Three named private files contain the closed request, intent and resource
inventory. An independent canonical request digest binds both other canonical
digests, the existing private upgrade-plan raw-byte digest, operation UUID and
exact root/history directory identities. File bytes and private single-link
identities are checked before invocation and afterward. The fixed engine retains
its existing private-plan, resource, artifact, schema and kernel checks. Changing
these input files cannot change the already admitted in-memory intent; a later
changed-input observation refuses rather than claiming unchanged caller inputs.
There are no arbitrary commands or callback fields.

Nonterminal execution requires the actual owner inside the already enrolled
driver group before the engine publishes responsibility. The existing installation
history and journal own action stages. The command cannot allocate or adopt a
database, group, original installation or provider resource. Previous recovery
still requires exact schema compatibility and actual public function; forward
repair repeats migration and internal/public probes under the same intent.

A same-intent terminal call reports historical completion or recovery without
opening the journal or asserting new readiness. Existing failed responsibility
is retained; recovery and forward repair are explicit fixed command choices,
never a caller-supplied action. Fixtures and terminal metadata cannot establish
actual installed function. Required verification includes actual CLI execution,
failure/recovery and unchanged terminal history, with exact operator/application
identity and separately scoped current CI.

Standalone execution exposed native/web and edge-guardian processes ending with
their launching session. Fixed process launches now create an independent OS
session while retaining the exact enrolled kernel group. Whole-group stopping
still governs shutdown. The success summary uses the actual native/web readiness
service identities and publishes only closed probe metadata.

Actual CLI execution on a disposable installation passed all seven stages.
Independent sessions verified public readiness, authorized and anonymous-refused
private API reads, CA-verified HTTPS Git and pinned-key SSH Git after launcher
exit. A wrong artifact digest refused at inspection while preserving the original
pointer and runtime process births; fresh public function and explicit compatible
recovery passed. A second operation lost its exact controller to SIGKILL after the
migration command launched. Same-intent forward repair repeated migration and
internal/public probes, preserved interruption events and completed. Six terminal
calls per completed/recovered case preserved 93, 115 and 146 history files.

Eight Linux command checks and one Windows early-refusal check passed; the full
Linux operator suite passed 143 checks with twelve foreign-profile skips. The
322-file private archive passed digest readback and actual credential exclusions.
All six case copies contain the same 26 operator files; committed applicability
and required CI are separate gates. The installed clean application is ea3a2ad,
with the same artifact and fifteen-migration schema throughout these CLI cases.
This does not substitute for a distinct-version migration or power-loss proof.

Enrollment, allocation, cancellation, managed Cloud and complete release gates
remain independent work. Initial fixture enrollment and input preparation use
fixed libraries; all upgrade action stages use the actual CLI. Fixture cleanup
stopped only the exact enrolled groups and retained databases, stores, artifacts,
histories and credentials. No running shell or agent service is introduced.
